## 0. Что меняет v2: честный аудит v1

v1 зафиксировал правильную **цель** и правильные **модули**, но содержал три инженерные фантазии в механизме. v2 сохраняет цель, модули и идентичность проекта (RAM Ring, тритный вакуум `0x79`, сценарии А/Б/В) и заменяет механизм на физически реализуемый.

| Утверждение v1 | Вердикт | Как в v2 |
|---|---|---|
| «Тёплая парковка» голого `ntoskrnl` в RAM при передаче железа Linux | **невозможно**: инициализировавшееся ядро NT считает своими таблицы страниц на всю физическую RAM, IDT/APIC, HPET/TSC, ACPI (модель OSPM предполагает единственного владельца машины) и GPU через WDDM; ядро Linux, стартовав рядом на голом железе, перепрограммирует APIC и таймеры — «припаркованное» ядро при пробуждении получит мусор вместо машины. Два голых ядра на одной памяти = взаимное разрушение (история coLinux) | Парковка **на уровне VM** (suspend/snapshot/resume тривиален и безопасен); ядро NT живёт в своей гостевой физике под EPT |
| «Обмен за наносекунды» между ядрами | наносекунда — это такт L1; реальный межъядерный IPC — единицы микросекунд | Doorbell через арбитра ~1–5 мкс; полезная нагрузка — на скорости памяти через общее окно RAM |
| «Любой `.exe` за 0.001 сек» | фантазийная цифра | 0.5–2 с на тёплой VM; «мгновенность» UX = прелаунч скрытого шелла Windows, который держит окружение прогретым |
| Прямой `MmMapIoSpace`/`ioremap` одного физического окна обоими ядрами без арбитра | окно живёт, но без арбитра его не защитить от перезаписи и взаимного саботажа | Окно выделяется `poler-boot` при POST и обслуживается арбитром: EPT-маппинг окна в обоих гостей (read/write), остальная память каждого гостя изолирована |
| Демо «DUAL-POST» (C#-консоль, 23.10) | **макет**: печатало строки в Windows-консоли; не UEFI, не два ядра | Признано макетом; настоящий прототип — Стадия 0 (§9) |

**Что переносится без изменений (сильная часть v1):** цели UX (двойной клик по `.exe` на Linux-столе = нативное исполнение настоящим ядром Windows), четыре модуля (`poler-boot` → `poler-hv` → `poler-bridge` → `poler-engine`), структура `POLER Shared RAM Ring` (§11), сценарии А/Б/В (§10), изоляция сбоев Linux-контура от Windows.

## 1. Постановка задачи (формулировка владельца)

> «Нужна ОС, которая загружается до Windows, работает в фоне и даёт из-под Linux запускать Windows-приложения, которые обрабатываются настоящим ядром Windows, прошедшим POST. На ПК физически три ОС: запущенный Windows, запущенный Linux и ОС-Транслятор, который транслирует для Linux всё из ядра Windows. Это решит проблемы — в том числе анти-читов — и соединит Windows и Linux навсегда. Технологии пока не существует, но её можно создать.»

Разложение на проверяемые требования:

* **Т1. Три субъекта.** Менеджер-ОС (ОС-Т) + Windows + Linux одновременно на одной машине, три полных ядра в RAM.
* **Т2. Windows-жилец.** Настоящее ядро NT, настоящие драйверы, штатная цепочка инициализации `bootmgfw.efi` → `winload.efi` → `ntoskrnl.exe` → HAL; лицензионная, обновляемая Windows.
* **Т3. Linux-стол.** Linux — видимая рабочая среда; сервисы ядра NT доставлены в Linux как **нативные**: смонтированные тома, `.exe` двойным кликом, окна Windows в составе Linux-рабочего стола, звук, буфер обмена.
* **Т4. Подлинный POST.** Windows получает подлинные таблицы инициализации своей платы (ACPI/SMBIOS/GOP), а не эмуляцию чужого железа.
* **Т5. Stealth.** Ядерные анти-читы (Vanguard, EAC) не должны видеть слой ОС-Т под Windows.
* **Т6. Связь навсегда.** Сервисная шина NT↔Linux — не сеть и не RDP-подобный протокол, а общее окно RAM со скоростью памяти.

               │  • Shared RAM Ring — сервисная шина (§11)
               │  • НЕВИДИМ для Windows (stealth, §6)
               │  • транслирует услуги ядра NT для Linux (§3)
═══════════════╪═══════════════════════════════╪════════════════

На одной машине физически живут три ядра: менеджер (мегабайты), Windows (гигабайты), Linux (гигабайты). «Три ОС» выполняются буквально.

## 3. Роли модулей = таксономия проекта

Таксономия ролей проекта (транслятор / экстрактор / мост / арбитр) ложится на модули один-к-одному:

| Модуль | Роль | Что делает | Чего НЕ делает |
|---|---|---|---|
| `poler-boot.efi` | **Экстрактор** (stage-0) | Стартует из `\EFI\POLER\poler-boot.efi` сразу после POST. До `ExitBootServices()` снимает **подлинные** таблицы платы (ACPI RSDP/XSDT, SMBIOS, GOP, memory map), вырезает окно RAM Ring (`EfiReservedMemoryType`), передаёт всё менеджеру, отдаёт управление | Не транслирует вызовы, не остаётся резидентным после старта жильцов — его данные живут в менеджере |
| `poler-hv` | **Арбитр** (партиционер) | Resident-менеджер в VMX root: делит физические ядра CPU, память через EPT, устройства (passthrough vs эмуляция); подаёт Windows подлинные таблицы из экстрактора; прячет себя (§6); обслуживает парковку VM (§4) | Не является «гостевой ОС», не имеет своего стола, не заменяет жильцам драйверы |
| `poler-bridge` | **Мост** (транспорт) | Агенты `poler-bridge.sys` (Windows) и `poler_bridge.ko`/демон (Linux) по краям кольца; очереди, doorbell, синхронизация, zero-copy передача буферов | Не решает политику запуска и не переводит пути — это судья транслятора |
| `poler-engine` | **Транслятор смысла** (IP проекта) | Судья Gateway (`Allow/Confirm/Block`), перевод путей `C:\…` ↔ `/rootfs/…`, манифесты `.poler`, губернатор ресурсов (RSS/CPU/таймаут), ABI/JIT-слой, UX запуска «двумя кликами» | Не управляет железом — всё железо уже поделено арбитром |

Формула разделения труда: **арбитр транслирует машину, мост транслирует сообщения, транслятор транслирует смысл.** Комбинировать их в одном бинарнике не нужно — связность через кольцо и есть архитектура.

## 4. Парадигма: виртуализация механизмом, нативность интерфейсом

На x86-64 существует ровно два способа посадить два полных ядра на одну машину:

1. **Арбитр в VMX root** (Intel) / SVM (AMD), делящий привилегии аппаратно — EPT/NPT для памяти, расширения для прерываний (APICv/AVIC), перехват привилегированных операций.
2. **Оба ядра рядом в Ring 0 без арбитра** — путь coLinux: взаимная перезапись IDT, APIC, таймеров, ACPI; машина умирает взаимным разрушением. Могила.

Третьего механизма не существует. Поэтому требование «не виртуализация» выполняется **не отказом от механизма, а сменой семантики**:

* Windows **не знает**, что ей транслируют (stealth, §6): CPUID без hypervisor-бита, подлинные таблицы платы, passthrough-устройства без virtio-подписей.
* Linux **не видит** виртуальную машину: он видит нативные сервисы — смонтированные NTFS-тома, `.exe`, запускаемые как родные файлы, окна Windows, растворённые в его рабочем столе.
* «Виртуальный рабочий стол» существует только у Windows-жильца — и не в окне VM, а как источник окон для Linux-стола.

Следствие для парковки: «тёплая пауза» Windows из v1 физически возможна **только на уровне VM** — suspend/resume гостя с сохранённым состоянием RAM. Это дёшево (копирование диффа страниц), надёжно (состояние ядра консистентно) и обратимо. «Тёплая пауза» голого ядра на общем железе — нет (§0).

Язык важен: гипервизор — это транслятор **железа** (одна физическая машина → две виртуальные машины: EPT транслирует адреса, vAPIC — прерывания, модели устройств — железо, планировщик — физические ядра в vCPU). Поэтому название «ОС-Транслятор» остаётся честным: проект транслирует машину (слой арбитра), сообщения (слой моста) и смысл (слой движка).

## 5. POST и подлинность железа

Требование Т4 («ядро проходит настоящий POST») закрывается экстрактором, а не эмуляцией:

1. `poler-boot.efi` стартует сразу после POST **этой** платы, пока живы UEFI Boot Services.
2. Снимает оригиналы: RSDP/XSDT/FADT/MCFG (ACPI), SMBIOS/DMI, GOP-режим, memory map, таблицы MP/PCIe.
3. Вырезает окно RAM Ring как `EfiReservedMemoryType` (никто не перезапишет, никто не выгрузит).
4. Передаёт снимки менеджеру и грузит менеджер.

Дальше Windows-жилец получает при старте **снимок подлинных таблиц своей платы** — а не сгенерированный OVMF-суррогат со строками «OVMF», «QEMU», «SeaBIOS» в SMBIOS. С точки зрения Windows и её драйверов это та же самая материнская плата, на которой прошёл POST: те же GUID, те же PCI-устройства, тот же DMI. Менеджер лишь разметил, какие ресурсы платы достаются жильцу.

Честная граница: физический POST выполняется один раз для всей машины; «Windows прошла POST» означает *получила подлинные результаты POST своей платы и штатную цепочку инициализации загрузчиком* — что и требуется по Т2/Т4. Альтернатива «второй физический POST для Windows» потребовала бы аппаратного сброса платы и убила бы Linux-стол — это несовместимо с Т1.

Исторический прецедент парадигмы: Microsoft прошёл путь WSL1 (сисколл-транслятор в ядре NT, заморожен из-за текучести семантики по углам) → WSL2 (настоящее ядро Linux в VM). POLER OS-Т — зеркало этого пути в другую сторону: настоящая Windows под Linux-столом, но с stealth-арбитром и без VM-семантики в интерфейсах.

## 6. Stealth и анти-читы (честная секция)

Базовый KVM+OVMF+virtio-стек детектируется стоковыми проверками мгновенно: hypervisor-бит в CPUID, строки «OVMF/QEMU/SeaBIOS» в SMBIOS, OUI-префикс MAC 52:54:00, virtio-подписи в PCI-конфигурации. Vanguard/EAC достаточно любого из них. Схема ОС-Т — другая лига:

* **CPUID** перехватывается менеджером: hypervisor-бит скрыт, Windows идёт по «нативным» веткам кода.
* **SMBIOS/ACPI** — подлинные таблицы платы от экстрактора (§5); досмотру нечем зацепиться.
* **Устройства** — passthrough настоящего железа в PCIe (VFIO), без эмуляторных подписей; то, что не критично, скрывается целиком.
* **Выходы** редки (APICv/posted interrupts), тайминговый шум — единицы наносекунд на редких выходах.

**Что остаётся детектируемым в принципе:** джиттер на перехватах, артефакты EPT-скрытия памяти (TLB-сайд-каналы, INVEPT-паттерны), косвенные следы планировщика. Это **гонка вооружений**, открытая с 2006 года (Blue Pill, Йоанна Рутковска): «недетектируем в принципе» обещать нельзя, «недетектируем стоковыми проверками» — можно и должно.

**Юридическая честность:** сокрытие слоя под ядерным анти-читом нарушает ToS игры; обнаружение = бан аккаунта. Решение по каждому титулу принимает владелец. Для игр без ядерного анти-чита (Police Simulator и абсолютное большинство) риска нет.

Вывод: композиция никем не собрана (интуиция владельца точна), но она собирается из существующих проверенных блоков. «Создать» здесь означает «собрать и доказать», а не «изобрести новую физику».

## 8. Настоящие сложности — не там, где кажется

Партиционер — **не** самая тяжёлая часть: Xen — десятки лет наработок, Jailhouse и rust-vmm (`vm-memory`, `kvm-ioctls`) дают скелет. Самые тяжёлые части стека:

1. **Оконный мост.** HWND → окно Linux без RDP-лагов: репарентинг/перекомпозиция окон Windows в Linux-рабочий стол через Shared RAM Ring, с вводом (клавиатура/мышь/IME), фокусом, z-order, drag&drop, перетаскиванием между «мирами». RemoteApp — компромиссный костыль на переходный период. **Вот где «технологии не существует» в самом чистом виде — и вот главный IP проекта.**
2. **GPU на обе стороны стола.** Одна карта, два потребителя; потребительского SR-IOV на массовых картах нет. План: dual-GPU (iGPU — Linux-стол, dGPU — Windows-жилец через VFIO passthrough) + Looking Glass для игр; virtio-gpu для не-игровых сцен.
3. **Скрытие** — не точка, а процесс (§6): каждая волна детекта — контрмера.

Ирония в пользу проекта: самая новая и самая сложная часть (перевод смыслов, мост, судья, манифесты) — это ровно слой, где уже написаны 400 000+ строк `poler-engine` (`wincompat`, ABI/JIT, Gateway-судья, `.poler`-контейнеры). Партиционер — commodity-обвязка вокруг готовой IP.

## 10. Сценарии использования (перенос из v1, исправленная механика)

* **Сценарий А (Windows-стол → Linux-программа/`.poler`-коробка).** `poler-engine.exe` кладёт задачу в очередь `Win → Lin`. Linux-жилец исполняет ELF внутри `poler-box` (`unshare` + `pivot_root` + `seccomp`). Падение/паника Linux-контура изолирована арбитром: Windows не шелохнётся, Linux-контур перезапускается за секунды.
* **Сценарий Б (Linux-стол → Windows-программа/игра `.exe`).** `poler-engine` кладёт команду в очередь `Lin → Win`. Настоящее ядро Windows (штатная инициализация, подлинные таблицы платы §5) исполняет `.exe` нативно: 100% совместимость с драйверами и `ntdll.dll`, ноль эмуляции. Окно публикуется на Linux-стол (Стадия 1: RemoteApp; Стадия 3: оконный мост). Анти-чит видит нативную машину (§6, с оговоркой ToS).
* **Сценарий В (Отладка Транслятора).** Из Windows (`poler-engine.exe --gateway`), из Linux (`poler-engine --gateway`) и на этапе POST (`poler-boot` автономное меню): состояние кольца, счётчики пакетов, переводы путей, вердикты судьи, профиль ресурсов жильцов. Автономный режим `poler-boot` (калькулятор `[N:D]`, просмотр памяти) сохраняется как в v1.

## 11. POLER Shared RAM Ring (сохранение структуры v1)

Физическое окно, вырезаемое `poler-boot` при POST (`EfiReservedMemoryType`, выровнено по 2 МБ). Идентично v1 по формату — меняется способ доставки в жильцов: окно проживает в памяти менеджера и маппится обоим жильцам через EPT (гостевая физика → хост-физика) с полным доступом read/write; остальная память каждого жильца изолирована. Агенты `poler-bridge` по краям работают с окном как с обычной памятью.

```text
Окно POLER Shared RAM Ring:
┌──────────────────────────────────────────────────────────────────────┐
│ 0x0000..0x0FFF (4 КБ)  : Заголовок PolerRingHeader                   │
│   • magic              : "POLER_OS" (0x534F_5245_4C4F_505F)          │
│   • version            : 2                                           │
│   • vacuum_byte        : 0x79 (121 — тритный вакуум 00000_3)         │
│   • win_state / lin_state : статус готовности жильцов                │
│   • win_to_lin_head/tail  : атомарные указатели очереди Win → Lin    │
│   • lin_to_win_head/tail  : атомарные указатели очереди Lin → Win    │
│   • doorbell_win / doorbell_lin : регистры уведомления (мс-масштаб   │
│     заменён на честный: уведомление через арбитра, 1–5 мкс)          │
├──────────────────────────────────────────────────────────────────────┤
│ 0x1000..0x200FFF (2 МБ): Кольцевая очередь команд и RPC Win → Lin    │
├──────────────────────────────────────────────────────────────────────┤
│ 0x201000..0x400FFF (2 МБ): Кольцевая очередь команд и RPC Lin → Win  │
├──────────────────────────────────────────────────────────────────────┤
│ 0x401000..Конец окна   : Zero-Copy область данных (.poler, .t5c,     │
│                          кадровый буфер окон, аудиопоток)             │
└──────────────────────────────────────────────────────────────────────┘
```

Кольцо — это транспорт без владельца-«гипервизора» в данных: заголовок и очереди знают только жильцы и агенты моста. Менеджер не читает содержимое кольца (его дело — EPT-разметка и doorbell), что упрощает stealth и уменьшает поверхность атаки.

## 12. Риски и честные ограничения

1. **Гонка вооружений stealth (Т5).** Недетектируемость «в принципе» невозможна; цель — опережать стоковые проверки анти-читов. Риск бана аккаунтов за нарушение ToS игр — на владельце.
2. **GPU-разделение.** Без dual-GPU производительный путь для игр — passthrough + Looking Glass; одиночная карта на два стола = компромиссы (virtio-gpu). 
3. **Оконный мост — исследовательская задача** (Стадия 3): полуфабрикатов в индустрии нет; RDP-подобные решения — временная мера.
4. **Объём работ Стадий 2–3** измеряется годами даже при темпе владельца. Стадийность (§9) защищает от «большого взрыва»: ценность подтверждается уже на Стадии 0.
5. **Лицензионная чистота**: Windows в составе ОС-Т используется по лицензии Microsoft (штатная активация); Linux — GPL; POLER-код — Source-Available по LICENSE проекта.

## 13. Чем проект НЕ является (защита названия)

* Это **не** «BIOS-персона» и не набор UEFI-утилит: после stage-0 экстрактор завершает работу.
* Это **не** эмулятор и **не** Wine: ни одной инструкции Windows не эмулируется и ни один Win32-вызов не переводится в пользовательском режиме — исполняет настоящее ядро NT.
* Это **не** «VM-коробка»: у жильцов нет VM-семантики в интерфейсах (никаких «виртуальных машин» в UX, no VM-manager GUI); Windows и Linux для пользователя — одна машина.
* Это **транслятор**: машины (арбитр), сообщений (мост) и смысла (движок). Название «ОС-Транслятор» — точное.
